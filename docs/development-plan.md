# WineSnap Development Plan

Revision: 1.1. This is the current, user-approved source of truth for future
development in this repository. Earlier dated inventories and pilot plans remain
historical evidence, not competing task queues. Safety/runbook restrictions in
AGENTS.md still apply. This document contains no credentials or private user data.

## Locked Decisions

- Develop the existing app in Codex, never Lovable. Retain React/TanStack,
  the owned Windows Postgres/Auth/Storage backend and the selected dark design.
- Finish the existing core before adding weekly planning or shopping lists.
- The delivery target is the owner's own local Windows app, not invited/public
  beta. The owned internet connector and its recovery flag stay disabled.
- Keep WineSnap as the working name. Food and wine remain equally important.
- The long-term scope includes the entire Chef/Cook/KetoLens vision: planning,
  pantry, nutrition, optional Keto, voice, meal photos and manual measurements.
- Voice may use an explicitly activated cloud service when needed. No raw-audio
  storage in WineSnap; disclose provider processing before actual use.
- Local hosting/data do not imply local AI inference. Retain the existing
  approved server-side provider integrations; no silent model/provider changes.
- Never change old production, the abandoned hosted test, DNS, root credentials,
  passwords or OS security settings on a generic continuation request.
- Portable off-device copies and actual second-PC recovery remain deferred.
  Public hosting, mobile login, store packaging, payments and branding are parked.

## DEV-01: Durable Project Plan

Owner: Codex. Deliver one canonical plan, not another dated alternative.

- Link it from AGENTS.md and README.md. Project instructions must require reading
  the board/current handoff before each continuation and updating it after work.
- Each task retains its ID, priority, dependencies, acceptance and evidence.
  Record plan changes and reasons without erasing earlier decisions.
- Check relative links, current scope and lack of secrets; commit/push on the
  existing development branch without merging or deploying old production.
- Acceptance: the roadmap and exact next action can be recovered from the repo
  without remembering the chat. Do not promise universal memory outside it.

## DEV-02: Dependable Local Access

Owner: Codex. Reuse Open/Check/Status and the real bound owner account.

- Open must focus/restore an existing viewer instead of silently doing nothing.
  Use bounded private current-user IPC, not an anonymous HTTP owner endpoint.
- Handle ordinary startup delay by resuming only the exact verified existing
  core containers. Never provision missing roots, start Docker globally, restart
  the shared engine or enable a connector. Keep the existing session/data.
- Distinguish starting, ready/authenticated, signed out, backend unavailable,
  closed and interrupted/stale states. Preserve explicit logout; never replace
  it with an unrequested fresh grant while the viewer is open.
- Show a safe actionable startup error; no raw exception, token, cookie, URL
  grant, profile, password prompt or silent retry of a destructive operation.
- Acceptance: unit/IPC tests and synthetic browser lifecycle checks; actual
  local owner readiness when it is safe to open a fresh viewer. Never close a
  real viewer containing potentially unsaved work to install the helper.
- No Windows reboot test without a separate request. Source verification,
  synthetic acceptance and installation into the owner's viewer are distinct.

## DEV-04: AI And Memory Quality

- Evaluate label identity, recipe generation/adaptation, contextual Chef,
  sommelier and recommendations using a fixed, bounded evaluation set.
- Reuse separate food/wine/history contexts and source-linked signals. Test weak

- Keep uncertain facts unknown and enforce existing food/allergen/health safety
  boundaries; schema-valid text is not proof of safe advice.
- Add content-free per-action model/usage/latency/error visibility, preserving
  current quotas. No prompts, photos, private memory or health values in logs.
- Acceptance: deterministic tests plus separately labelled bounded live-provider

## DEV-06: Weekly Planning And Shopping

- Private plans carry date/meal, exact recipe version and servings. Later edits
  to a recipe must not silently rewrite an existing plan.
- Derive editable shopping lists deterministically; combine only compatible
  ingredient units and retain unknown amounts. No guessed volume/weight density.
- Support manual items, checked items, reload and normal revision conflicts.
- Acceptance: scaling/aggregation tests, ownership/RLS, offline/reconnect and the
  complete plan-to-list-to-cooking browser flow.

## DEV-07: Pantry And Household Use

- Confirm actual ingredient/amount/unit stock and last confirmation separately
  from habitual staples or stale observations. Never deduct stock silently.
- Reuse existing diner preferences within the local owner's account; do not
  introduce external accounts/invitations into this local delivery.
- Require explicit review of consumption and relevant meal variations. Keep
  adult dietary/wine choices separate from child profiles.
- Acceptance: stock freshness, units, explicit consumption, diner isolation and
  ingredient-to-recipe/list flows without invented availability.

## DEV-08: Nutrition And Optional Keto

- Extend the existing curated references with reviewed sources, versions,
  licensing and confirmed ingredient/preparation/edible-weight mappings.
- Preserve nullable nutrients, EU/US fiber distinctions, final-step rounding and
  unknown density. User confirmation does not turn an estimate into measurement.
- Standard stays default. Keto is voluntary; comparisons/adaptations require
  review and do not promise ketosis or medical suitability.
- Acceptance: calculation/source integrity and substitution tests, privacy and
  adult/child boundaries. Health journaling remains separate from this phase.

## DEV-09: Swedish Cook Mode Voice

- Explicit microphone start/stop and visible listening state. Keep buttons/text
  available; actually verify device/language support before enabling voice.
- Cloud transcription is permitted when needed through the authenticated local
  server and existing provider, with separately configured voice workload.
- Use bounded audio turns; no WineSnap raw-audio files/logs. Disclose external
  processing and check current supplier handling before real microphone use.
- Deterministic commands control existing cooking actions; ambiguous/destructive
  commands require confirmation. Contextual help uses the existing Chef scope.
- Acceptance: real Swedish commands and interruptions on the owner's PC after
  human microphone approval. A microphone icon or mocked transcript is not proof.

## DEV-10: Food And Meal Photos

- Separate food output contracts from wine-label recognition. Present proposed
  items/portions with uncertainty and manual correction before logging.
- Distinguish image-estimated, recipe-calculated and manually measured values.
  Never infer freshness, allergen safety or actual ketosis from a photo.
- Retain photos only on explicit save, in private food-specific storage/access
  paths, never public wine shares. Extend export/deletion/backup coverage.
- Acceptance: known-image quality checks, confirmation/edit/discard flows,
  owner isolation, photo deletion and honest handling of unknown quantities.

## DEV-11: Optional Meal Goals And Measured Ketones

- First complete a separate safety/data-protection review and explicit owner
  opt-in. Begin disabled and test with synthetic measurements only.
- Separate real measurements by method/unit/time from meal estimates and ordinary
  taste memory; do not combine incomparable blood/breath/urine trends.
- No diagnosis, treatment, automatic child restriction, public sharing, analytics
  logging or automatic AI transfer of measurements.
- Extend private schemas, UI controls, retention, export and deletion together.
- Acceptance: method/unit validation, opt-in/off and privacy tests plus reviewed
  activation. A request to continue does not waive this review gate.

## DEV-12: Complete Local Delivery

- Verify planning -> shopping/pantry -> recipe -> cooking/voice -> wine ->
  feedback/history, including the optional domains that have passed review.
- Finish performance, accessibility, safe update/rollback, local operating guide
  and isolated recovery for the complete installed schema and saved media.
- No Lovable access, manual Git steps or renewed password enrollment is needed
  for normal local development/use. Preserve the known off-device limitations.
- Acceptance: current source/CI and installed browser evidence plus actual owner
  use; the complete local scope is done, not automatically a public release.

## Common Engineering Rules

- Additive, owner-scoped schema/API changes only; existing Auth/RLS, recipe
  revisions, conflict handling, model boundaries and feature gates remain.
- Test migrations in isolated CI/local clones and retain a verified backup/
  rollback before an actual owned update. Never destructively test the real owner.
- Typecheck, lint, Vitest, synthetic build/runtime, client budget and database
  safety remain required as relevant. UI evidence uses synthetic fixture images,
  never exported owner screenshots, browser sessions, HARs or credentials.
- Distinguish source-complete, installed, automated-verified, live-provider and
  human-verified evidence. Timeouts/aborted runs are not passes.
- Prefer focused local tests and full CI when the PC is under load. Do not slow
  the owner's app with concurrent heavy checks or weaken limits to hide failures.
- Ask only for consequential missing input: new costs/suppliers, sensitive real
  collection, security reduction, potential data loss or a changed main goal.
- Continue within approved scope without repeated permission prompts. Commits
  and pushes stay on the development branch; no automatic merge or publication.
